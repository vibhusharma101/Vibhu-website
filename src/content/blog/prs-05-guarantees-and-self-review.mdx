*Part 5 of 5 — How I built PRS. Four posts got to a reviewer that's honest, well-informed, cheap and learning. This last one is the gap between "usually right" and "trustworthy" — and the best story in the project.*

Everything so far makes PRS good *most of the time*. Trust lives in the gap between "most of the time" and "you can rely on it," and closing that gap means converting good behaviours into **guarantees** — properties that hold by construction rather than by hoping.

---

## Guarantee one: nothing posts without surviving a challenge

Between merge and post sits an **adversarial verify gate**. Every merged finding gets re-checked by a verifier against the actual file contents at HEAD — plus the grepped definitions of the symbols it references — and has to survive an explicit attempt to refute it.

The mechanism is straightforward. What I'd actually emphasise is the **rollout**, because a gate is exactly the kind of component that can quietly hurt you while its dashboard looks great:

- It shipped in **shadow mode** first. The verifier ran fully and its verdicts were logged, but posting still used the unmodified findings. Measurement at zero risk.
- Then **confirm mode**: confirmed findings post with the verifier's confidence; refuted ones post as *visible advisories with the refutation attached*. Nothing is dropped — you see the gate's verdict on every finding, and there's no chance it's silently hiding a real bug while you evaluate it.
- Only then **enforce**. And even there, a refuted MAJOR-or-above security, tenancy, auth or money finding is demoted to an advisory rather than dropped.
- Fail-open at every layer, deliberately: a gate outage can never lose a review.

That last pair of decisions is the one I'd defend hardest:

> **Build gates that can only ever downgrade confidence, never delete evidence.**

I'd rather a human dismiss a hedged warning than never see a real one. A gate that deletes findings is a gate whose false-positive rate you can never measure, because the evidence of its mistakes is exactly what it threw away.

## Guarantee two: a hook that can't walk away with work unfinished

The newest piece is small, and it makes a perfect case study.

I wanted a guarantee that an assistant working on a PR can't end its turn while review comments sit unanswered or CI is red. So: a **Stop hook** that refuses to let the turn end.

One design constraint shaped everything. A Stop hook can only make the agent *continue* — it cannot sleep, wait, or poll. So it blocks **only on actionable work** (an open thread, a red check), which the agent can actually reduce, so the loop provably converges. It never blocks on a merely-*pending* re-review, which would spin forever. And it's opt-in via a sentinel file, so it never traps unrelated sessions.

Since its entire purpose is to *be* a guarantee, one property dominates everything else: **an unverifiable state must never let it quietly disarm.**

Which is exactly what I got wrong.

## The day PRS reviewed its own guardrail

I shipped that hook as four PRs — one per repo — and PRS reviewed them. Which meant PRS was reviewing the guard built to enforce its own correctness.

The round-2 catch is still my favourite thing any reviewer has ever told me. `block()` — the primitive whose entire job is to stop the turn — called `jq`. So the branch handling *"`jq` is missing, therefore block"* produced no output and allowed the stop. **The safety net had a hole shaped exactly like the thing it was catching.**

The fix is four lines, and it's the shape I now reach for whenever a guard depends on a tool:

```bash
# block() must work even when the tool it needs is the thing that's missing
block() {
  if command -v jq >/dev/null 2>&1 && jq -cn --arg r "$1" '{decision:"block",reason:$r}'; then
    exit 0
  fi
  printf 'PR watch (block): %s\n' "$1" >&2
  exit 2            # exit-2 also blocks — no jq required
}
```

Round 4 is the one that genuinely surprised me, because it wasn't finding a bug in my original code — it was finding a bug in my *fix*. I'd made "CI returned no rows" keep the hook armed, which reads as the safe choice. But a repo with no checks configured would then never be able to disarm, and the loop could never terminate. I'd traded a fail-open bug for an infinite loop, and PRS caught the trade.

**17 → 17 → 15 → 5 → 0. Fifty-four findings, every one addressed**, each fix landing with a test until the suite reached seventeen mocked cases.

And exactly one finding I *didn't* fix: an ambiguous `git` state with no reliable shell-level distinction between "not a repository" and "corrupted metadata." I reasoned-**accepted** it as a known limitation, in writing, on the thread.

That last decision matters as much as the fixes. A reviewer — human or machine — that can't distinguish "must fix" from "acceptable known limitation" isn't thorough. It's stuck, and it will hold your release hostage to a case that cannot happen.

## Shipping to four repos without a broken window

Worth a short note, since multi-repo rollouts fail at the seams rather than in the code. Three things worked:

- **The hardening landed inside the feature, not after it.** The fix PR targeted the feature branch, so the capability could never merge un-hardened. There was no window in which the un-fixed version existed on a main branch.
- **Version pin and consumer code travel in the same commit**, so there's never a moment where a repo requests a capability from an engine version that ignores it.
- **I leaned on a tolerance property**: an unknown Action input is a *warning*, not an error. That made merge order completely free across five repos, with zero coordination.

## What I'd tell someone starting this

**1. Precision is an epistemics problem before a model problem.** The highest-leverage artifact in the whole system was the rules-of-evidence prompt, not the model choice. Constrain what it may claim before you reach for something smarter.

**2. Never call context "authoritative" unless code guarantees its integrity.** Degrade whole-section or not at all, and make "absent" a safe state the system already handles.

**3. Store the facts, derive the views.** One row per file is easy to keep correct; the searchable index is rebuilt from it and therefore can't drift.

**4. Instrument first, then improve.** Every feature in this series traces to a number on the weekly scoreboard. Swapping a gentle occasional audit for a harsh weekly one was itself one of the biggest improvements I made.

**5. Verify your loops end-to-end.** A feedback loop you haven't proven changes an output is decoration.

**6. Know when to stop.** Five rounds could have been fifty. Fix genuine correctness bugs, reason-accept the exotic and safe-degrading residuals — and write down why.

## The through-line

Go back to the four failure modes from [Part 1](/blog/prs-01-the-audit-that-humbled-it), and every later chapter is one of them answered by **structure rather than cleverness**: forbid unverifiable claims, honour the team's conventions, collapse duplicates, force real effort — then feed it guaranteed context, route spend without lowering the bar, learn from every reaction, and prove each guarantee in code.

None of it needed a smarter model.

What it needed was treating *"does the team trust the next comment?"* as the only metric that matters, and building backward from there — which turns out to be a much harder discipline than upgrading a model, and the only one that compounds.
