*Part 3 of 5 — How I built PRS. [Part 2](/blog/prs-02-panel-of-specialists) made the reviewer honest by forbidding claims about code it can't see. This post is about giving it more to see — without giving back the honesty.*

After the v2 rewrite, the weekly numbers said something uncomfortable. The reviewer was now *safe*, and it was **missing things a human would catch.**

When I read through the misses, they had one thing in common. Every one depended on context sitting just outside the changed lines:

- the full list of allowed values for an enum the diff branches on,
- the exact shape of a record the diff constructs,
- who *else* in the repo calls the function the diff just changed.

Rule 10 was working exactly as designed, and that was the problem. The fix couldn't be "relax the rule" — that just brings back confident hallucination and undoes Part 2. It had to be: **expand what's visible, then lift the hedge only for what I'd actually shown it.**

That took two systems, answering two different questions.

---

## System one: the per-PR definition resolver

The first answers *"what are the exact schemas, enums and functions this diff names?"*

For each PR, a small per-repo script extracts those definitions and injects them into the prompt as an authoritative block. Then the base rules flip: for symbols shown in that block, the hedge is **lifted** — assert normally, because I handed you the ground truth.

The shared Action stays stack-agnostic. It exposes exactly one input, and each repo ships its own extractor:

```yaml
# consumer repo's workflow — the ONE generic input
referenced-definitions-command: 'python3 .github/prs-refdef.py'
```

The effect is the clearest before/after I have from the whole project. Same bug, same model, same diff — the only variable is whether the reviewer was *allowed to know* one enum.

### The part I'd defend hardest in a design review

Here's the trap, and I want to be precise about it, because it's the most interesting decision in the project.

The prompt now tells the model this block is **authoritative** — *"don't claim a missing enum case unless you've enumerated the full member set shown here."* That instruction is only **sound if the block is actually complete.**

If the extractor crashed halfway and handed over a torn, half-written enum, the model would follow its instructions *correctly* and emit confident, false "missing member" findings. I would have rebuilt the exact noise this feature exists to kill — and stamped it with authority, which makes it strictly worse than where I started.

So the trust boundary is enforced in code, not by hoping the extractor behaves. First, the resolver runs caged:

```bash
# any failure discards partial output entirely
timeout 120 bash -c "$REFDEF_CMD" || {
  echo "soft-failed — passes run without it"
  : > "$OUTPUT_FILE"
}
```

Then again at injection time, before a single token reaches a prompt:

```python
# prepare_referenced_definitions()
#  1. header missing?          → prepend "## REFERENCED DEFINITIONS" (rules key on it)
#  2. over REFDEF_MAX_BYTES?   → clamp at the last COMPLETE ## / ### section boundary,
#                                then append an explicit note: "further definitions were
#                                dropped — rule 10 applies to symbols not shown"
#  3. no section boundary fits → drop the block entirely
#                                (torn-but-authoritative is worse than absent)
```

Note what step 2 refuses to do: it never truncates mid-section. It clamps to the last *complete* boundary and then explicitly tells the model that more was dropped, which hands those symbols back to rule 10. And if it can't find a boundary that fits, it throws the whole block away rather than ship a partial one.

The principle generalises well past this feature:

> **Never tell a model to trust something unless code guarantees that thing is whole.**

A *missing* piece is safe — it degrades to a hedged question, which the system already knows how to handle. A *broken* piece treated as authoritative is the dangerous case. Design for that, and "authoritative context" stops being a footgun.

Four repos, four languages, so four extractors — ORM model schemas and enums for the backend; TypeScript interfaces, types and enums for web; Kotlin data classes, enums and sealed hierarchies for Android; Swift structs, `CodingKeys` and enum cases for iOS. Each is dependency-free, byte-budgeted, and soft-fails to empty.

Each also taught me a parsing lesson the hard way. The Android extractor initially false-matched Compose built-ins like `Text` and `Default` as repo symbols — which matters enormously when the output is labelled authoritative. A false symbol in a trusted block is the torn-enum problem wearing a different hat.

## System two: a whole-repo map, built with tree-sitter

The second system answers a different question: *"if I change this, what else might break?"*

That needs a map of the entire repository, which is far more than a per-PR script should build inline. So: parse **every** source file with **tree-sitter**, via a language pack that bundles grammars for all our stacks, so one code path reads Python, TypeScript, Kotlin, Swift, Go and Java.

For each file, record what it *defines* and what it *uses*:

```python
LANG_BY_EXT = { ".py":"python", ".ts":"typescript", ".tsx":"tsx", ".js":"javascript",
                ".kt":"kotlin", ".swift":"swift", ".go":"go", ".java":"java", ... }

DEFINITION_NODES["typescript"] = {
    "function_declaration":"function", "class_declaration":"class",
    "interface_declaration":"interface", "enum_declaration":"enum", ... }
# walk the tree once for definitions, once for references — plain depth-first,
# "first child → next sibling → parent"
```

That gets stored as **one row per file, per commit**. The searchable "who-uses-what" map is **derived from those rows at read time, not stored.**

### Why derive instead of store

That was a deliberate call, and it's the design decision I'd most want to keep.

A per-file row is **self-contained**. When a file changes, you re-parse it and overwrite its one row. Anything that file stopped using vanishes for free, because it's simply not in the new list. There is no cleanup step to forget.

The flipped map has the opposite shape. It pools contributions from across the whole repo, so a single file edit ripples into scattered entries: add this file to `computeTotal`'s entry, remove it from `Order`'s, then check whether anything *else* in the file still uses `Order` before you remove it… Miss one of those and the map doesn't crash. It **silently lies** — and a silently wrong dependency map feeding a code reviewer is a great way to generate confident nonsense about blast radius.

> **Store the simple facts. Derive the fast lookup on read.**

It also makes the cache genuinely incremental: keyed by commit SHA, a push re-parses only the files in its diff and reuses everything else.

The payoff is the search. *"Which files use `computeTotal`?"* becomes one dictionary lookup — **O(1)** — instead of grepping the whole repo, **O(N)**, per symbol, per review. That map is what powers the cross-file pass: take the symbols the PR changed, look up their dependents, rank them, and hand the reviewer *"you changed `computeTotal`; `routes/api.js` calls it and still expects the old shape."*

---

## Two systems, one job

| | Definition resolver | Tree-sitter symbol map |
|---|---|---|
| **Question** | the exact schema/enum this diff *names*? | which files across the repo *relate* to this change? |
| **Scope** | tiny, per-PR, injected inline | whole-repo, cached per commit |
| **Gives** | depth | breadth |
| **Approach** | dependency-free per-repo script, soft-fails to empty | real parser — correctness over the whole tree matters |

Depth plus breadth. And because rule 10 still governs everything, the reviewer only ever speaks confidently about context I can verifiably show it — with code, not convention, deciding what counts as "shown."

Context is what made PRS genuinely good. It's also what made it expensive: ten passes plus two context layers, running on every push, is real money — and a reviewer that costs too much gets throttled, which quietly makes it a worse reviewer.
