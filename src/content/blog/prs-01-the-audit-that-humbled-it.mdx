A reviewer I wrote once read a 58,000-token pull request and approved it in about two and a half seconds.

It spent 27 output tokens doing it. Something to the effect of *"No issues found, the changes look good."* I found it in the logs weeks later. There was no thinking behind it — the model had been handed a large, genuinely complex change, skimmed it, and told the author it was fine.

That reviewer was **PRS**, the code review system I built at Powerplay. This is the build log: what I shipped, what broke, what the numbers said, and what I changed because of them. Five parts, in the order it actually happened.

Part 1 is the first version, and the audit that told me how far off I was.

---

## v1: three passes, and good enough to be dangerous

The first architecture was about as simple as it could be. A GitHub Action fires on an activation comment, fetches the diff, and runs three sequential LLM passes:

1. **Quick Scan** — a fast, broad sweep for obvious problems.
2. **Deep Review** — a slower, more careful read.
3. **Cross-File** — how the changed files connect to each other.

Around that sat the operating model that has survived every rewrite since: **opt-in activation**, because nobody wants a bot barging into every PR; a **label** so subsequent pushes trigger incremental reviews of just the delta; and **skip rules** for trivial or empty diffs so it doesn't burn money arguing about a README typo.

It shipped. It caught real bugs. People used it.

And it was quietly losing their trust, in a way no dashboard was going to show me.

## The audit: 350 comments, graded by hand

The temptation was to guess at what was wrong. Instead I pulled seven weeks of merged PRs and scored **every single bot comment** as Good, OK, or Invalid. By hand. It took a weekend and it was the highest-leverage thing I did all year.

The 81.2% is the number people quote back at me, but it was never the point. **The point was that grading 350 comments by hand forced me to categorise *why* the bad ones were bad.** Four patterns fell out, and every architectural decision in the rest of this series traces back to one of them.

---

## Failure 1 — confidently discussing code it cannot see

A diff hands the model roughly three lines of context around each change. It cannot see the model schema, the enum's full member list, the imported helper, or the base class.

Asked to review, it asserts things about all of them anyway. *"This field doesn't exist."* *"This enum is missing a case."*

Sometimes right. Often guessing. And one confident-but-wrong *"this doesn't exist"* costs more trust than ten good comments earn — because the engineer now has to verify everything, which is the exact work the reviewer was supposed to save. This was the single biggest source of invalid findings.

## Failure 2 — flagging our own conventions as bugs

Every codebase mandates patterns of its own: a required response wrapper, a dependency-injection idiom, rules about how scoping gets derived, a transaction discipline.

The worst comments in the whole audit were the ones that flagged a **mandated** pattern as a bug, then helpfully proposed "fixing" it into the exact thing the guidelines forbid. Inverted, and delivered with total confidence.

Nothing makes an engineer mute a tool faster than being lectured about house style by something that has never read the house rules.

## Failure 3 — saying the same thing five times

Run several checks over one diff and they independently rediscover the same issue, phrased differently, on slightly different lines. One audited week carried roughly **90 duplicate findings**.

Every one of them can be individually correct and the wall of near-identical comments still reads as noise. Later, once I built a weekly scoreboard ([Part 4](/blog/prs-04-cheap-and-learning)), duplicates ranked as the single biggest drag on precision.

## The thesis I took away

Staring at those four categories, the fix I'd been assuming — *use a better model* — was obviously wrong.

Three of the four aren't intelligence failures at all. The model wasn't too dumb to know the enum's members; it was **never shown them**. It wasn't too dumb to respect our conventions; it was **never told them**. It didn't rubber-stamp because it lacked capacity; it rubber-stamped because **nothing forced it to spend any**.

Those are failures of *permission* and *context*, not of reasoning. So the thesis for v2:

> Precision is an **epistemics** problem before it's a **model** problem. Constrain what the model may claim; give it exactly the context it needs to claim more, safely; and prove every guarantee in code rather than convention.

Which maps to the rest of this series:

- **[Part 2](/blog/prs-02-panel-of-specialists)** — replace one generalist prompt with a panel of focused passes, and write a rules-of-evidence contract that makes speculation structurally expensive. *(Failures 1, 2, 3, 4.)*
- **[Part 3](/blog/prs-03-seeing-past-the-diff)** — build two context systems so the reviewer can see past the diff, with a trust contract enforced in code. *(Failure 1 from the other side: the findings it was **missing**.)*
- **[Part 4](/blog/prs-04-cheap-and-learning)** — make it cheap enough to run on every push, and make it learn from pushback.
- **[Part 5](/blog/prs-05-guarantees-and-self-review)** — turn good behaviours into hard guarantees, and let PRS review its own guardrail.

There's one more thing the audit gave me, and it mattered more than the 81.2%: **the habit of scoring the reviewer's output on a schedule.** Every improvement in this series got chosen because a measurement demanded it, not because it seemed like a good idea. That discipline is the actual product. The code is downstream of it.
